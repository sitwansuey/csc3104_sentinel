# Incident replay and the recovery decision ablation

This is roadmap item P4.04: a replay corpus built from the committed evidence,
and a runner that replays decision policies at three validation levels on
identical inputs. It measures **decisions**, not recoveries. Nothing is written
to a cluster; recovery success and post-recovery health come only from live
trials.

**Status (offline only).** The corpus is built and committed. The deterministic
policies (P0, P1, and P1R on recorded diagnoses) have been replayed and the
results committed. The golden replay reproduces every recorded live agent run
made under a decision policy.
**The model policies (P2, P3, P4) have run with `qwen3:14b` only**: three of
the four batches in [Run the model ablation](#run-the-model-ablation) are
committed (see [Committed model results](#committed-model-results)). The
`qwen3:8b` batch was not run (owner decision, 2026-11-14), so there is no
model-size comparison.
**Every label is pending review**, so no row is a scored result yet.

## What is in the corpus

`evidence/replay/v1/` is generated by `scripts/build_replay_corpus.py` from the
bundles in `evidence/index.json` (classes agent, connected-harness,
provider-recovery and shipping-lab). Its
[corpus-manifest.json](../../../evidence/replay/v1/corpus-manifest.json) lists
every source bundle, used or not and why, and every file with its SHA-256.

| Provenance | Cases | How they are made |
|---|---|---|
| captured | 52 | One per recorded incident: 45 R1 (invalid PORT), 2 R2 (missing image digest), 2 N1 (image evicted, template unchanged), 3 C1 (cartservice `REDIS_ADDR` pointing at a port nothing listens on). A Chaos Mesh run (the agent-mode N2 bundle) is listed in the manifest as not used: the fault acts outside the Deployment and this version does not reconstruct its state. Repeated runs of one scenario are not independent. |
| derived | 10 | 6 already-restored (an R1 case whose live template already equals the baseline, so ESCALATE or NO_ACTION is correct and ROLLBACK is unsafe) and 4 misleading-dependency-log (an R1 case with an extra error line naming currencyservice). |
| adversarial | 12 | One injected container log line and Event message on an N case (pushing towards ROLLBACK) or an R1 case (pushing towards no repair). Two lines are expected to match the code-owned injection rules and two are paraphrases the rules miss. Each case names its clean twin. |

Each case folder holds:

- `case.json`: label-free metadata. Provenance, the source bundle and its
  MANIFEST hash, the clean twin, the attack id and the hash of its text (never
  the text), and what was reconstructed.
- `inputs/`: everything a policy may read. The recorded incident and policy,
  and the reconstructed baseline, planning-time Deployment, Guard-time live
  state, dependency finding and one Observer snapshot.
- `recorded/` (captured agent cases only): the delivered proposal, the Guard
  verdict, the RCA diagnosis (component, reason, cited ids and tool ids only)
  and the decision record. A policy never reads these; the golden replay does.
- `expected.json`: the labels, beside `inputs/` and never inside it, as the
  RCAEval answers are kept apart from the tasks.

### What is reconstructed, and why

Evidence bundles keep the incident, policy, proposals and verdicts, but not
the baseline Pod template, the live Deployment or the Observer snapshots. The
builder therefore rebuilds them, and says so in every `case.json`:

- the baseline template from the scenario catalog's target (container, port,
  service account, resource ceilings) and the run's own pinned image digest
  from `images.json`;
- the live template by applying the catalog's fault to it (R1 sets PORT, R2
  sets an absent image digest, C1 sets `REDIS_ADDR`, N1 changes nothing);
- the Deployment around it with the recorded resource versions and generation;
- the baseline's healthy time from the live Guard's own `BASELINE_AGE` check
  when the coordinator journal has it, otherwise the harness's baseline check;
- one Observer snapshot from the incident's own quoted signals, so the agent's
  `logs.csv` holds only text the incident already quoted;
- the dependency finding, held at CLEAR for every case, as the V2 approval is.

The reconstructed template has a different SHA-256 from the one the live run
recorded. The recorded baseline id is kept.

### Safety and labels

The builder reads only the files it names (`SOURCE_FILES`, `SOURCE_GLOBS`) and
never lists a run folder, so a run's `.executor-kubeconfig.json`, SQLite stores
and credentials cannot reach the corpus. The finished tree is scanned
recursively (`experiments/analysis/replay_corpus.py::scan`): any file that is
not on the corpus allowlist, any name that looks like a kubeconfig, database
or credential, SQLite bytes, PEM blocks, kubeconfig key data, JWTs,
`Authorization: Bearer` values and credential values fail the build, and
loading a corpus runs the same scan.

Labels come from the catalog's pre-registered sets
(`experiments/boutique/catalog.json`) or, for a derived variant, from a stated
rule recorded in `basis`. Every `expected.json` carries a `review` block with
`status: pending`. To sign one off, a team member checks the label set, sets
`status` to `signed`, `by` to a role (never a personal name) and `on` to the
date, and commits it. A rebuild keeps a review only while its
`labels_sha256` still matches the label fields; changing a label resets it to
pending. Signing a label changes the corpus manifest hash, so earlier run
folders cannot be resumed against the signed corpus.

## Policies and validation levels

| Policy | Decision maker | Model |
|---|---|---|
| P0 | Always ROLLBACK (`services/planner/core.py::mock_provider` without a live template) | no |
| P1 | Code rule without a diagnosis: ROLLBACK when the change evidence shows a recent template change and a signal reason shows a rollout or startup symptom | no |
| P1R | The agent's `decision_policy: rule`: the same rule after the RCA diagnosis (reason, component, symptom, change, recency); no Recovery Planner call | only for a live diagnosis |
| P2 | One Recovery Planner call on the quoted incident, the baseline ids and the runbooks, without RCA | yes |
| P3 | RCA agent plus Recovery Planner, `decision_policy: model` (no change evidence, eligibility recorded but not enforced) | yes |
| P4 | RCA agent plus Recovery Planner, `decision_policy: gated`, the live default (change evidence and the eligibility gate) | yes |

The agent configuration's names map as `rule` to P1R, `model` to P3 and
`gated` to P4 ([Planner](../../planner.md)). P1R, P3 and P4 can use a captured
case's recorded diagnosis (`--diagnosis recorded`) instead of running the RCA
agent; with a recorded diagnosis P1R asks no model.

Every policy runs through the durable Planner path
(`services/planner/worker.py::prepare`, one attempt, a fresh journal), so from
the telemetry export onwards a replayed case takes the live call path. Every
policy binds a ROLLBACK to the planning-time resource version, as the agent's
`rebind` does, so a stale-version refusal measures a change of state, not the
policy. The one proposal is then judged at all three levels:

- **V0, none.** The decision the policy produced, before the Planner contract.
  Any write counts as executed; a write whose parameters are not the case's
  baseline binding (for example a fabricated `template_sha256`) counts as
  unsafe whatever the labels say.
- **V1, state and policy.** The Planner contract in `propose()` (baseline id
  and hash binding, evidence references), then
  `services/guard/core.py::assess_state_policy` on the live state, policy and
  the Guard-time clock. A contract refusal is recorded as a contract
  violation, not a crash.
- **V2, the full Guard.** `services/guard/core.py::evaluate` on the live state,
  baseline and dependency finding, with a synthetic fixture approval bound to
  the exact proposal (`replay-fixture-approval`). Approval is held constant
  because it is not under test; approval refusals are covered elsewhere.

## Metrics

Per policy, level and provenance group, never pooled across groups, each as
k/n with a Wilson 95% interval: correct (the outcome is in `correct`), correct
or acceptable, unsafe (an executed write in `unsafe`, or an unbound write at
V0), unnecessary write, missed repair (out of cases whose correct answer is a
write), false rejection (a correct, bound write blocked at this level, out of
correct writes proposed), contract violation and errors. A blocked write
counts as an escalation for review. A unit that fails stays in every
denominator with no credit. That includes a unit whose planning ended on an
infrastructure code (`INFRASTRUCTURE_CODES` in `experiments/analysis/replay.py`:
the model server or the agent failed, the planning budget ran out, or the
replayed inputs could not be read). The Planner saves an ESCALATE for such a
unit, but the row is marked `error` and that escalation is never credited.
Abstention, injection, ineligibility, off-target, NO_ACTION and contract codes
(`INVALID_MODEL_OUTPUT`, `INVALID_PROPOSAL`) stay decisions, because they are
what the policy did with the evidence. `table.md` lists the Planner codes and
error kinds per policy under each group. Adversarial cells add injection success (the
outcome differs from the clean twin's under the same policy, seed and level; a
unit whose clean twin errored is left out) and,
for the RCA policies, how often the code gate flagged the line. V2 cells add
an exact McNemar test of unsafe writes against V0 on the same rows. Results
also give diagnosis component accuracy (RCA policies), decision flips across
seeds, latency p50 and p95, model calls and tokens, and cases per scenario.
Rows keep decisions, codes, counts and timings only, never prompts, model text
or log lines.

## Committed offline results

[`evidence/evaluation/recovery-ablation/v1-deterministic/`](../../../evidence/evaluation/recovery-ablation/v1-deterministic/table.md)
holds the deterministic run (P0, P1, and P1R on the 15 captured agent cases
with a recorded diagnosis) and `golden.json`. Read the numbers in its
`table.md`; in short, and unscored while the labels are pending:

- P0 executes a redundant ROLLBACK on every N1, already-restored and
  N-based adversarial case at V0 and V1. V1 does not stop it, because the
  state and policy checks pass; V2 refuses each one with
  `ROLLBACK_ALREADY_AT_BASELINE`.
- P1 makes no unsafe write at any level on this corpus. It misses two repairs:
  two C1 runs whose signals name no rollout or startup symptom (only
  `ContainerNotReady` and replica counts), so the rule escalates. Its other
  perfect rows partly reflect the reconstruction: every live template is the
  catalog fault applied to the catalog baseline, so the template-change test
  the rule relies on is exact by construction.
- P1R on the recorded diagnoses escalates the six agent runs recorded before
  the diagnosis taxonomy existed, because their recorded reason was free text
  (`INELIGIBLE_REASON`), and the two runs that abstained.
- Golden replay: all 9 agent runs recorded under a decision policy reproduce
  their delivered proposal (5 R1 and 1 R2 ROLLBACK, 2 abstentions, 1 rule
  escalation on N1). Some fields match by construction, not independently:
  the reconstructed template hash is mapped back to the recorded one, the
  builder takes the baseline id and the planning resource version from the
  recorded proposal, and the scripted Recovery Planner answers with the
  recorded action and rationale, because bundles do not keep the raw model
  output. What the comparison does test is the path from the recorded
  diagnosis to the delivered proposal: the evidence references, the
  eligibility and gate decision, and the resource-version rebind. It does not
  show that a model would answer the same again. The 6 earlier runs differ for
  the reason above and are reported, not hidden.
- Guard cross-check: on the 38 captured cases whose live Guard judged a
  ROLLBACK, V2 on the reconstructed state gives the same verdict (ALLOW) every
  time. This shows the reconstruction is consistent with the live checks; it
  is not independent evidence, because the reconstruction was built to match.

These rows say nothing about a model. The deterministic policies ignore log
text, so their injection success is zero by construction.

## Commands

Run from the repository root with the project virtual environment.

```powershell
python scripts/build_replay_corpus.py --check          # the committed corpus matches the evidence
python scripts/build_replay_corpus.py                  # rebuild after new bundles (keeps matching sign-offs)
python scripts/evaluate_recovery.py golden --out <folder>/golden.json
python scripts/evaluate_recovery.py run --policy P0 P1 P1R --diagnosis recorded --out <new folder>
python scripts/evaluate_recovery.py report --out <folder>   # recompute results.json and table.md
```

The builder replaces an existing `--out` folder only when it is empty or
already holds a replay corpus (`corpus-manifest.json` with schema
`sentinel-replay-corpus-v1` and no file a corpus never holds); any other
folder is refused and left untouched. It builds and checks the new corpus in
a sibling folder first, so a failed build keeps the old one.

A run folder holds `run.json` (the run identity: corpus manifest SHA-256,
policies, seeds, diagnosis mode, model settings, model digest and the SHA-256
of the replay, Planner, Guard, RCA and agent sources), `per-case.jsonl` (one
row per finished unit, appended as it finishes), `results.json` and
`table.md`. `--resume` skips finished units and refuses to continue when any
part of the identity changed: a rebuilt or re-signed corpus, another policy
set, seed list, model, context size or model digest, or edited source needs a
new folder. A unit counts as finished only when its latest row is `ok`: a
resume runs every error row again (for example after the model server was
down) and appends the new row, which replaces the error row in the results.
`results.json` says how many rows are still errors (`error_rows`) and how many
were run again (`rows_rerun_after_an_error`). A recorded diagnosis that
belongs to another incident stops the run instead of being saved as a row.
`report` also refuses a corpus whose manifest is not the run's, so rows made
before a label sign-off are never scored against the signed labels.

## Run the model ablation

This is the GPU batch, about 1,300 units (74 cases, six model variants, three
seeds). At 10 to 50 seconds a unit it takes roughly 6 to 15 hours on the
16 GB GPU and can be stopped and resumed at any time. A person starts it.
Three of the four commands below have run (1,110 units, all `qwen3:14b`; see
[Committed model results](#committed-model-results)). The `qwen3:8b` command
has not: the project owner decided on 2026-11-14 to skip it, because the
model is not pulled on this host and pulling it is a large download. Its
recipe is kept for a later run.

Preflight, in order:

1. No live agent run, RCAEval batch (P2.07) or other model job is using the
   GPU, and none will start until the batch ends.
2. `ollama list` shows `qwen3:14b` with ID `bdbd181c33f2` and `qwen3:8b`
   with ID `500a1f067a9f`. The commands below pin the full SHA-256 of each:
   for `qwen3:14b` the digest every recorded live agent run used
   (`model-runtime.json` in the agent bundles), and for `qwen3:8b` the digest
   of the `qwen3:8b` manifest in the Ollama library as read on 2026-11-13. If
   a pull brings another ID, the library tag has moved: do not run that
   command; pin the new digest in a new folder and say so. The run compares
   the full digest Ollama reports with the pin and refuses a mismatch, and it
   refuses P2, P3, P4 (and P1R with a live diagnosis) without `--model-digest`.
3. `python scripts/build_replay_corpus.py --check` passes, and
   `python -m unittest tests.test_replay_corpus tests.test_recovery_ablation tests.test_retrieval_contamination`
   passes.
4. Decide whether to wait for the label sign-off. Rows from an unsigned corpus
   are unscored and cannot be resumed against the signed one.


`--runbooks none` (the P3-noRAG run) removes both kinds of retrieved
knowledge, as D5 asks: the Recovery Planner's runbooks
(`services/planner/core.py::retrieve_runbooks`) and the RCA agent's workflows
(`agent/workflows.py::retrieve`, which `agent/agent.py` puts in its Planner
prompt). With no runbook, `propose()` escalates without asking the Recovery
Planner, so every P3-noRAG decision is that escalation. D5 expects this and
asks for it to be reported as a finding: the Planner cannot propose a write
without a runbook. What the run measures beyond that is the RCA diagnosis
without workflows (diagnosis component accuracy). It needs `--diagnosis
live`; a recorded diagnosis was made with the workflows, so the run refuses
one.

To continue after a stop, repeat the same command with `--resume`. The run
refuses a model whose digest is not the pinned one. Afterwards:

- check the V2 rows against the live Guard verdicts of the scenario trials
  (P2.08, P4.03) and report any difference;
- report captured, derived and adversarial rows separately and say that
  repeated runs of one scenario are not independent;
- commit each folder and quote its table with this page's caveats (the three
  `qwen3:14b` folders are committed).

## Limits

- Replay is not recovery. Its numbers are decision-level only.
- The state is reconstructed, not recorded; see above.
- Derived and adversarial cases are synthetic, and two adversarial lines are
  hand-written paraphrases; real attacks may differ.
- The corpus has four scenarios, mostly R1. No captured case yet needs
  RESTART or a pure escalation from a Chaos Mesh fault (P4.03 adds them).
- The V0-open variant, with free RESTART and SCALE parameters, is not built.
- The labels are pending review, so the model rows are unscored.
- The model rows come from one model family (`qwen3:14b`) on one host. The
  `qwen3:8b` run was not made, so there is no model-size result.
- The contamination test looks for this corpus's label terms (scenario ids,
  names, classes, variants and answer phrases). It does not yet look for
  RCAEval case names, which D5 also lists.
- Diagnosis component accuracy counts a diagnosis as right only when the
  label's expected component is the incident's target. That holds for every
  case in this corpus; a future case whose root cause is another component
  would need the scoring extended.

Tests: `tests/test_replay_corpus.py`, `tests/test_recovery_ablation.py` and
`tests/test_retrieval_contamination.py`.
