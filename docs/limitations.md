# Known limitations and defects

Sentinel is a single-host prototype. This page lists what it does not do yet
and the defects found in evaluation, so nobody has to discover them in a demo.

The register is [limitations.json](limitations.json). Everything between the
markers below is generated from it by `python scripts/evidence/summarize.py`;
do not edit it by hand. Each entry has:

- **kind**: `defect` (the code does the wrong thing) or `limitation` (missing
  scope, stated honestly);
- **status**: `open`, `mitigated` or `fixed` on this tree. Fixed entries stay
  as history and name the pull request;
- **evidence**: a `file:line` with the text expected on that line, a file, or a
  claim id from [evidence/claims.json](../evidence/claims.json);
- **planned**: the roadmap item that addresses it, and the GitHub issues.

`python scripts/evidence/limitations.py --strict` runs in CI. It fails when a
cited file is gone, a line no longer holds the quoted text or a claim id does
not exist, so a citation cannot silently go stale. To fix a defect, change its
status to `fixed`, add `fixed_by`, point its evidence at the test that proves
the fix and regenerate.

### L-EXEC-WEDGE

**A write rejected with its resource version unchanged waits in NEEDS_RECONCILIATION unless fencing is on.** Defect, mitigated; recorded 2026-11-11. Planned: P2.06, P5.08. Issues: #61.

- Impact: Fixed in code and verified live on one host: one run each for the moved-resourceVersion and replaced-target cases on 2026-11-11 and again at 4139385 (a plain delete was not run live), and the fence for an unchanged resourceVersion at 4139385 and 5409092 (C-EXECUTOR-WEDGE-FENCE). It stays mitigated because fencing is off by default. Reconciliation is a pure decision table: a deleted or recreated target, or a resourceVersion that moved without this action's evidence, ends SUPERSEDED, which the Coordinator records as FAILED so a new proposal can follow. The live wedge harness (C-EXECUTOR-WEDGE: one run per scenario on one Windows host with kind, 2026-11-11) showed main's Executor (d5b2ed9) staying NEEDS_RECONCILIATION over 5 reconcile passes with the workload still excluded, while 4afc879 resolved the moved-resourceVersion case (rv-race) as SUPERSEDED/ADVANCED_WITHOUT_EVIDENCE and the replaced-target case (delete-recreate) as SUPERSEDED/TARGET_REPLACED, released the workload and applied a second proposal. With the default kubectl transport, error text is still not classified, so a rejection that leaves the same UID at the same resourceVersion, such as an admission denial, still looks like a request in flight. The optional REST transport (P5.08) decides such a rejection at once as FAILED with basis DEFINITE_REJECTION, shown in four live admission-deny rounds (L-REST-TRANSPORT-OFFLINE); owner sign-off remains pending. When fencing is configured (fence_after_seconds; off by default), a reconcile pass after the settle delay sends a metadata-only patch with the same UID and resourceVersion tests and this action's fence marker, journaled before the call. If it commits, the write never committed and never can, so the result is CONFLICT with basis FENCED and the workload is released; tests and the model checker cover it, and the model checker ends no run in doubt with fencing on. With fencing off, that action stays NEEDS_RECONCILIATION and after 600 s gets one 'Operator action required' result. Live verification of the fence (C-EXECUTOR-WEDGE-FENCE, one host, kind-sentinel-boutique-connected): in the admission-deny scenario a ValidatingAdmissionPolicy denied the template write with the same UID at the same resourceVersion; the action stayed NEEDS_RECONCILIATION before the settle delay, then one fence committed and it resolved as CONFLICT/FENCED on 5/5 reconcile passes, the workload was released and a second proposal was APPLIED. The first run (4139385) is FAILED on one harness check only, which wrongly expected metadata.generation to stay unchanged (a Deployment bumps it on an annotation change); 17d4532 fixed the check to compare the spec and the rerun at 5409092 passed every check. One run per revision; the wedge summaries carry no provenance block, so these revisions are inferred.
- Workaround: Turn fencing on: fence_after_seconds in the Executor worker configuration, or --fence-after with runtime/live_executor.py --reconcile. With fencing off, an operator inspects the Deployment and clears the Executor ledger row by hand for the unchanged-version case. The deleted, recreated and moved-version cases need no workaround.

### L-EXEC-REDELIVERY

**A replacement Executor without the ledger row reported CONFLICT for a write that was applied.** Defect, mitigated; recorded 2026-11-12. Planned: P3.01, P4.01. Issues: #18, #58.

- Impact: Fixed in code; P4.01 S1c passed 5/5 at 3ba0d12 and S2 passed 5/5 at b37017e with one audit template write each and every invariant holding, unscored. An Executor that finds the resourceVersion moved now looks for this action's evidence annotation on the Deployment and reports APPLIED for a peer's write without writing again. A host given a reconcile command with no ledger row journals the action as in doubt and reconciles from the proposal and live state, so it never starts that write. An execute command on a fresh host can still write, and the resourceVersion test in the patch lets at most one write for the action commit. Decision-table and integration tests cover both. One gap stays: if the peer's write was later overwritten, execute() reports CONFLICT where reconcile() reports SUPERSEDED; the Coordinator records both as FAILED. The P3.01 multi-process harness runs two Executor processes with separate ledgers and locks on one host: in S1c a peer adopted a write committed by a crashed Executor and in S2 a stalled Executor adopted its peer's write, each with one template write. P4.01 used two Executors on different kind nodes against the real API server, but all four nodes share one Docker host; no run used separate machines.
- Workaround: Keep a separate ledger for each Executor and retain Coordinator ownership and conditional writes; the live kind results do not verify separate machines.
- Evidence: `services/executor/core.py:627`; `services/executor/core.py:459`; `tests/test_executor_reconciliation_table.py:420`; `tests/test_executor_reconciliation_table.py:475`; `services/executor/store.py:3`; `tests/test_distributed_processes.py:58`; `docs/distributed-acceptance.md`.

### L-CLOCK-ORDERING

**Lifecycle ordering compared wall-clock timestamps written by different components.** Defect, mitigated; recorded 2026-11-12. Planned: P3.03, P4.01. Issues: #18, #63.

- Impact: Fixed in code (P3.03); P4.01 S7 ran live in kind, unscored, with TimeChaos -300 s on both Executors: all 8 completed runs passed with FAILED and zero writes; an additional attempt aborted at operator restore (fixed 47e3aae). No run used separate machines. Worker results are now ordered by the Coordinator request they answer, not by the producers' clocks, so the wedge is gone: an answer to a superseded request gets HTTP 409 and is released, never resent for ever. Scenario S7 (both Executors on a gated test clock 300 s behind, separate processes on one Windows host, file mode, operator approval required) showed the wedge before the change (result refused with HTTP 400, incident READY). After it the result is accepted, but the Executor's own Guard re-check, which reads the same shifted clock, sees the Coordinator-stamped approval 300 s in its future and refuses: the action ends FAILED with no write and every invariant holding in 3 of 3 runs, with each Executor measuring an offset of 300.005 to 300.012 s. An Executor host whose whole clock is off by more than the bound therefore cannot complete an approved action; an in-bound peer can (S7b, 3 of 3 runs). Lease renewal now uses the lease length the Coordinator returns. Clocks still matter for freshness and expiry: the Guard tolerates a configured bound (max_clock_skew_seconds, off by default) and counts it against age and expiry; the Executor's local re-check and the Verifier's start check still compare their clock with timestamps from other processes, so skew beyond the bound ends an action FAILED or, by reading the code (no test), delays verification instead of wedging it. Workers measure their offset from the Coordinator (Cristian's algorithm) and, with a bound set, stop claiming and turn unready outside it. After a clock step this holds from the first exchange after the step: a request already claimed runs with the stepped clock until its next exchange, and a step smaller than the measurement uncertainty can go unseen. The offset is self-reported, so this guards against honest misconfiguration, not a dishonest worker. Messages accepted before store migration 4 have no high-water mark, so for an action in flight at the upgrade only the newest-request rule orders its results. Skew was injected on one host, including TimeChaos in kind; it was never measured between separate machines.
- Workaround: Keep host clocks synchronised (NTP), and set max_clock_skew_seconds for the workers and the Guard policy and --max-clock-skew-seconds for the Coordinator, so a host past the bound stops claiming work.

### L-AGENT-JOURNAL

**Agent mode bypasses the durable Planner journal.** Defect, mitigated; recorded 2026-11-11. Planned: P2.01, P3.07. Issues: #14, #54.

- Impact: Fixed in code: agent planning now runs through prepare() and the PlannerStore journal. A model failure is retried up to three times; an abstention, a diagnosis of another component, a NO_ACTION answer or a target changed during inference ends at once. Every failure ends in a saved, delivered ESCALATE, so the incident moves to NEEDS_REVIEW, and a saved proposal replays without another model call. Still open: the planning budget applies per attempt, so one incident can use three budgets. The remote Planner worker now has an agent mode with the same hooks and journal (P3.07), tested offline only, as one OS process on one host with a fake model server. That ESCALATE guarantee covers only failures after a passed model preflight. In remote agent mode a model that is unreachable when the worker is about to claim never starts an attempt: there is no retry and no exhausted ESCALATE, and the incident stays OPEN (not NEEDS_REVIEW), its request unclaimed, until a ready agent Planner claims it. An outage that starts inside a cached preflight window (30 s by default) may use up attempts and escalate, or leave the incident OPEN once the cached check expires; which one happens depends on timing. Saved results are still re-sent while the model is down, except a proposal saved only in the Planner journal before the worker stopped, which waits for the next passed preflight. No bounded escalation for a long model outage exists (for example a Coordinator-side planning timeout); adding one is an owner decision. Verified live on one host for the harness agent mode's failure paths: from 4139385 every failed agent run ended in a saved, delivered ESCALATE with the incident in NEEDS_REVIEW and zero Executor writes, and each bundle's planning-status.json records the attempts, the error code and delivered 1. These are an off-target diagnosis at 4139385 (DIAGNOSIS_OFF_TARGET, C-AGENT-AUTOLAB-4139385), a forced 1 s planning budget that escalated BUDGET_EXCEEDED after three attempts (C-AGENT-FORCED-ESCALATION) and two abstentions at 870aa7d (C-SCENARIO-LIVE-UNSCORED). The retry after a failed model call also ran live in two passing runs: in boutique-live-20261111t221204z-602449 (C-AGENT-AUTOLAB-4139385) the Analyzer's call and in N1 at dab3b3f (boutique-live-20261112t080756z-29fd09, C-SCENARIO-LIVE-UNSCORED) the Reporter's call failed in attempt 1 after about 45 s and 2048 output tokens, and attempt 2 completed, reaching RECOVERED and the expected rule escalation respectively; each planning-status.json records 2 attempts. A lost delivery replayed after a restart has not been exercised live. Agent bundles before 4139385 predate the journal, so those failed runs left the incident OPEN. Decision (17 Nov 2026): the per-attempt planning budget is kept, with up to three attempts, because it fails closed into an escalation. The configured aggregate for one planning row with the shipped defaults (planning_budget_seconds 600, max_attempts 3, retry_seconds 5) is 3 x 600 s + 5 s + 10 s = 1815 s of planning budgets and scheduled backoff. This is not a wall-clock deadline to a saved escalation: polling, target and telemetry I/O, persistence and restart/lease recovery can add delay, and remote preflight outages can leave the request unclaimed indefinitely. For A attempts, budget B and retry_seconds R, the configured aggregate is A x B plus the sum of min(3600, R x 2^(i-1)) for i = 1 through A-1. A re-plan after a stale Guard refusal has its own row and aggregate. Remote model-outage handling stays a recorded limitation.
- Workaround: For runs recorded before this change, read the run's summary.json and dashboard event, then handle the incident by hand. The harness removes the fault as an administrator restore, which is not Sentinel recovery.

### L-AGENT-APPROVAL

**No live run yet shows a person approving through the authenticated API.** Defect, mitigated; recorded 2026-11-11. Planned: P2.02, P2.03. Issues: #10.

- Impact: Fixed in code for the four live harness paths: the Executor experiment, Boutique walkthrough, provider mode and agent mode now create approvals through the authenticated approval API, served per run by a child process with generated tokens, and the Executor's final pre-write lookup reads them through ApprovalClient. Revocation, expiry or a stopped authority therefore fails closed with zero writes, and agent mode no longer records a pre-authorised approval. An interactive run needs a person to type the exact action ID; an unattended run must opt in to auto-lab approval, recorded under the automated-lab identity and never as a person. Agent and provider modes plan through the durable Planner journal and approve through the same session, and an agent run with --expect escalated asks for no approval and starts no authority. A Boutique run with the dashboard's lab controls can instead use ui approval: the dashboard shows the pending action, the operator types its action ID and clicks Approve or Revoke, and the dashboard server relays the decision with the run's operator credential (dashboard-operator by default); the browser holds only the lab session token, which any local process can also read, so it does not identify a person. This is proven offline with the real child process and a fake Kubernetes API, for agent mode and, since P2.04, for provider mode (run_provider_case with a real provider subprocess). Live on one host from 4139385, automated only: the connected walkthrough and the agent runs approved through the authenticated approval API in auto-lab mode, recorded under the automated-lab identity with human false (C-CONNECTED-HARNESS-AUTOLAB, C-AGENT-AUTOLAB-4139385, C-AGENT-AUTOLAB-5409092), and a reject-mode negative test stopped with one refusal, no approval and no Executor record for the refused action (C-APPROVAL-REJECT). Still no evidence shows a person approving: interactive and ui approval have not run live, and live bundles before 4139385 used pre-authorised lab approval. The file-backed negative cases still give the Executor a fixed approval record that never reaches the Coordinator; they prove refusals only. The Executor experiment's rival-process check reads a file copy of the managed record, not through ApprovalClient; the target lock refuses it before it reads the approval. The Verifier acceptance script (scripts/validation/test_verifier_connected_live.py) still calls the local approve() and reads the record straight from the store; it is outside this fix.
